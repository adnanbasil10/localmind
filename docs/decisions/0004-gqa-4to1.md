# ADR 0004 — GQA at 4:1 (8 query heads, 2 KV heads)

**Status:** Accepted · **Context:** §6

## Decision

8 query heads, 2 KV heads, head_dim 64.

## Why — the number to quote

KV cache bytes per token, fp16:

| Scheme | KV heads | Bytes/token | @2048 ctx |
|---|---|---|---|
| MHA | 8 | 16 KB | 32 MB/seq |
| **GQA 4:1** | **2** | **4 KB** | **8 MB/seq** |

4× more concurrent sequences in the same memory. Concretely: it is the difference between the
server fitting inside a Docker container's memory limit and not.

Decode is **memory-bandwidth-bound**, not compute-bound — every generated token re-reads the
entire KV cache. Shrinking the cache 4× attacks the actual bottleneck. Shrinking the parameter
count would not.

## Cost

Some quality, measured rather than assumed: the ablation reports the val-loss delta against MHA at
matched parameters. Report it honestly even if it is worse than hoped.

## Why not MLA

DeepSeek's latent KV compression is strictly more sophisticated and compresses further. It is
listed as a stretch goal, not a baseline, because GQA is what Llama 3 and Qwen 3 actually ship and
the comparison table is more useful than the extra compression.
